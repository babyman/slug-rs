# Agent Evaluation

This harness measures whether three agent-facing features help an agent
write and review Slug: the [value JSON form](../../docs/reference/value-json.md),
the [capability report](../../docs/reference/capability-report.md), and
[diagnostics](../../docs/reference/diagnostics.md) with stable codes, ranges,
expected and actual values, and fixes. It runs a coding agent, Codex by
default or Claude Code, headless on small tasks, once per feature arm and several times each, and records what happened.

## Tasks

- `tasks/` holds 22 coding tasks. Each has a `task.md` prompt, a
  `reference.slug` solution, and `cases.json`. The agent writes
  `solution.slug`; the harness then runs it on every case and compares its
  output with the reference's. The first case uses each `cfg` default from the
  prompt; the others are hidden inputs supplied through a `slug.toml`, so a
  hard-coded answer fails.
- `review/` holds 6 review tasks. Each has `before/` and `after/` versions of
  a program and an `answer.json`. The agent decides whether the change gives
  the program new kinds of access, such as the filesystem or configuration,
  including access gained indirectly or by dynamic import.

- `projects/` holds larger exercises that produce something useful. `json/`
  asks for a JSON library, `json.slug`, specified in its `task.md`, which the
  agent receives as `spec.md` in its workspace. Its hidden
  suite, `cases.json`, has 109 cases covering parsing, correctly rounded
  numbers, parse errors and their offsets, canonical serialization,
  serialization errors, round trips, and large and deeply nested documents.
  Each case runs as its own program beside the agent's module, so a crash or
  hang fails only that case, and a run scores the fraction of cases passed.
  Cases may set a `generate` recipe, for documents too large to store, and a
  `seconds` time limit. `reference/json.slug` is `slug.fmt.json`, the
  library an agent wrote in the json-fixes-2 run, and passes every case. A
  case a reference is known to fail can be marked `reference_fails`. `jobs/` asks for a concurrent job
  runner, `jobs.slug`: dependency planning and validation, a concurrency
  limit, retries, timeouts, failures that skip dependents without stopping
  other jobs, and a log file. Its 52 cases are `program` cases: whole Slug
  programs, run after the suite's shared `prelude`, that print `PASS`; some
  depend on timing, with margins of tens of milliseconds. Its reference passes
  every case; `make_cases.py` regenerates `cases.json`. `tiny/` asks for an
  interpreter, `tiny.slug`, for Tiny, a small scripting language its `task.md`
  defines: integers, strings, lists, closures, and errors of six kinds at exact
  lines and columns. Its 115 cases, also generated by `make_cases.py`, each run
  one Tiny program, with expected results written from the specification
  rather than taken from the reference, which passes all of them. `mustache/`
  asks for a Mustache template renderer, `mustache.slug`: the official
  specification's required modules (interpolation, sections, inverted
  sections, comments, partials, set delimiters) and inheritance, without
  block reindentation, lambdas, or dynamic names, over Slug data, with
  syntax errors at exact lines. Its 223 cases, written by `make_cases.py`,
  are the specification's tests (v1.4.2, vendored in `spec/`) and cases for
  what `task.md` adds; each renders from text and from `parse`'s result.
  Project runs default to a $5 budget and a 45-minute timeout and
  use the coding arms.

The small coding tasks are a quick smoke check after language changes; the
projects are the main experiment.

Write new tasks without looking at how the features behave, keep some aside as
hold-outs, and replace a hold-out once it has driven a change.

## Arms

| Arm        | Diagnostics | Fixes   | `slug report` | Tasks          |
|------------|-------------|---------|---------------|----------------|
| `baseline` | text        | removed | blocked       | coding, review |
| `json`     | JSON        | removed | blocked       | coding         |
| `fixes`    | JSON        | kept    | blocked       | coding         |
| `testing`  | JSON        | kept    | blocked       | projects       |
| `report`   | text        | removed | available     | review         |
| `python`   | -           | -       | -             | `tiny`, `crawl` |

The `testing` arm is `fixes` plus `docs/language/testing.md`, a guide to
testing a program's logic in one `slug` run, which its prompt points to.

The `python` arm is a control: the agent implements the project in Python
from `python/task.md`, which `make_cases.py` writes from `task.md` with only
the interface changed, so both languages face the same definition. Its
workspace holds only `spec.md`, and any files in `python/workspace`. The same checks, written as data to
`checks.json`, are graded by `harness/projects.py` against `tiny.py`, one
`python3` process per check with the same ids and time limits as the Slug
cases, so results compare case by case. A game project such as `crawl`
instead ships `python/cases.json`, graded by `harness/python_game_grader.py`:
the same cases, played through the module's functions, comparing every
screen and the final snapshot. `python/reference/tiny.py`, a port of
the Slug reference, passes all of them. Agents also run Python to edit files, so a
record's `slug_runs` counts every command that runs Python and `program_runs`
splits them into scripts, `-c`, `-m`, and standard input. For Codex they come
from its command log, since its login shell puts `/usr/bin` ahead of the
`python3` wrapper (`harness/python_wrapper.py`), which logs them for Claude.
It runs under the interpreter running the harness, recorded as
`python_version`.

The agent's `slug` is a wrapper (`harness/slug_wrapper.py`) that applies the
arm: it forces or strips `--diagnostic-format=json`, removes fixes and the
edits of suggestions (keeping each suggestion's message) from JSON and text
output alike, and rejects `slug report`. Text diagnostics render the same
members as JSON ones, so since text output gained codes, expected and actual
values, and suggestions, text-arm runs from before then are not comparable
with later ones. Each arm's prompt and copied documentation mention only
the features it enables. After a failed run the wrapper reruns the command in
JSON mode, only to log its diagnostic codes, so every arm records which
failure classes the agent hit.

Since 2026-10-18 the Slug prompts also say that single-quoted strings are
raw, after agents in nearly every Tiny run wrote escapes inside them in their
own tests. Runs from before then are not comparable on that count.

## Running

```sh
# Check that every reference solution, including project references, passes its cases.
python3 eval/agent/harness/run.py check-references

# Show the runs a selection would start, and their worst-case cost.
python3 eval/agent/harness/run.py plan --arms baseline,fixes --tasks 01,04 --repeats 3

# Start them. Nothing runs without --yes.
python3 eval/agent/harness/run.py run --arms baseline,fixes --tasks 01,04 --repeats 3 --yes

# The Python control on the Tiny project.
python3 eval/agent/harness/run.py run --arms python --tasks tiny --repeats 1 --yes

# Summarize a finished or partial run.
python3 eval/agent/harness/run.py summarize eval/agent/results/<run>
```

`--agent` selects the agent: `codex` (the default) or `claude`.

A Codex run is `codex exec --json --ephemeral` in a fresh workspace, sandboxed
with `--sandbox workspace-write` and no network: the agent may write only its
workspace, the temporary directories, and the wrapper's log directory, and web
search is disabled. `CODEX_HOME` is a temporary directory holding only a copy
of your `auth.json`, so your config, skills, plugins, memories, rules, and hooks
do not reach the agent; `--ignore-user-config` alone would still load skills and
plugins from your home. If a run refreshes the login, the refreshed copy is
written back to your `auth.json` afterwards, unless that file changed
meanwhile. Codex has no spending limit, so `--timeout-minutes` alone bounds a
run, and records have tokens but no cost. Its `num_turns` counts agent steps
(messages, commands, file changes, and other tool calls), which is not the
same measure as Claude Code's turns, so compare arms within one agent.
`--model` selects the model; without it Codex uses its built-in default, not
the one in your config.

A Claude run is `claude -p` in a fresh workspace with `--permission-mode dontAsk`,
the tools `Bash, Read, Write, Edit, Glob, Grep`, and `--max-budget-usd`
(default 1). By default it uses your normal login with
`--setting-sources project` plus settings that disable hooks and auto-memory
and exclude every CLAUDE.md, so your own settings, CLAUDE.md, memory, and
hooks do not reach the agent. `--setting-sources` alone still loads
`~/.claude/CLAUDE.md`. With `ANTHROPIC_API_KEY` set,
`--bare` isolates it further. `--model` selects the model and `--jobs` runs
several at once. `--tasks` takes name prefixes and matches coding and review
tasks alike, so `--tasks 01` selects both `01-fizzbuzz` and `01-add-file-log`.

The full default plan is 234 runs. Start with a few tasks and repeats.

## Results

Results go to `eval/agent/results/<run>/`, which git ignores:

- `runs.jsonl`: one record per run with the task, arm, repeat, pass or fail,
  cases passed, the agent and model, the agent's turns, tokens, cost (Claude
  only), and duration, the number of
  `slug` invocations and failures, and every diagnostic code logged.
- `<task>/<arm>/<repeat>/`: the agent's workspace, its full session output
  (`codex-stream.jsonl` or `claude-stream.jsonl`), and
  the wrapper's invocation log, for reading what happened.

A run that ends in an error after one or two turns, typically because access
ran out, is marked `infra_error` and left out of summaries.

`summarize` prints, per kind and arm, the pass rate, the mean project score, and mean turns, shell
commands, input and output tokens, cost, and wall time; then, apart, the mean
program runs (`slug_runs`) and failed runs; then every diagnostic code seen and
the tasks that failed. Program runs stay out of the headline because they
count processes: a test suite that starts one `slug` per check counts dozens
where a Python suite run in one process counts one. Agent output is noisy: compare
arms over several repeats, not single runs.
